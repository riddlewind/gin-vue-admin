## 关闭登录验证码（已实现并实测）

**原逻辑没有"关闭"选项**：`captcha.open-captcha`
- `0` = 每次登录都要（最严格，不是关闭）

- 负数 = 原来没有这个分支

**改动 3 个文件**：

2. `server/api/v1/system/sys_user.go` — `Login()` 里删掉重复的 Get/Set/判断，改调 `captchaRequired(c)`。
   - 之前两处逻辑各写一遍，改一处漏一处就会出现「前端不显示、后端仍校验」的错位，故抽公共函数。
3. `server/config/captcha.go` — tag 注释补充负数语义。

   - `IsOpenAIProvider()` 判断通道；`openAIEndpoint()` 校验三项配置并拼 `/chat/completions`
   - `buildOpenAIMessages()`：`{mode,query,inputs}` → `[system, user]`，inputs 序列化成 json 块

  `clientPages[{name,label,description,pageType,targetModules,fields[...]}]`
- `workflowPromptChat` 输出字段：`summary` / `steps[{title,goal,prompt,expectedOutput,suggestedTool,autoExecutable}]`
- 前端 `extractJson` 支持 ```json 围栏和裸 JSON，prompt 里要求围栏即可

**验证手法（可复用）**：写一个 Python mock 中转站监听 18999，实现 `/v1/chat/completions`
（按 body.stream 分别返回 SSE 分片或 JSON），再用临时实例 8899 跑真实链路。

## 接入真实中转站（sensenova）— 已端到端验证

**用户实际配置**（`server/config.yaml`）：
```yaml
autocode:
    ai-provider: sensenova          # 名字随意，非 gva 即走兼容通道
    ai-base-url: "https://token.sensenova.cn/v1"
    ai-key: "sk-..."                # 用户自己的 key，别写进文档/日志
    ai-model: "sensenova-6.8-flash-lite"
```

**踩坑：`ai-provider` 原本写死只认 `"openai"`**。用户配 `sensenova` 会被判成 gva 通道 →
`ai-path` 为空 → 报「请先前往插件市场个人中心获取 AiPath」。已改成：
```go
func IsOpenAIProvider() bool {
    p := strings.ToLower(strings.TrimSpace(global.GVA_CONFIG.AutoCode.AiProvider))
    return p != "" && p != AIProviderGVA   // 除 gva/空 外都走兼容通道
}
```
配套加了 `providerName()` 用于报错/返回体展示，替换掉所有硬编码的 `"openai"`。

**该中转站的真实行为（重要）**：
- 它不是商汤官方 API，是**聚合站**。`/v1/models` 返回 7 个模型：
  `deepseek-v4-flash`、`glm-5.2`、`sensenova-6.8-flash-lite`、`sensenova-u1.5-lite`、
  `kimi-k3`、`deepseek-flash`、`deepseek-v4.1-flash`
- **是推理模型**，SSE 的 delta 键为 `role` / `reasoning` / `content` 三个。
  思考过程在 `reasoning`，最终答案在 `content`。
  `ExtractOpenAIDelta` 只取 `delta.content` → 思考过程被自动过滤，**这是正确行为，别去“修”**。
- 实测耗时：短问答 10~35s，`analysisChat` 完整需求分析约 55s。

**端到端实测结果（临时实例 8899 + 真实中转站）**：
- `llmAuto` 非流式 → HTTP 200，`{"code":0,"data":{"answer":"...","provider":"sensenova"}}`
- `llmAutoSSE` 流式 → 525 帧 `event:message` / `data:{"answer":"..."}`，done 1 次，正文无思考过程
- `analysisChat` → JSON 合法，键 `summary/recommendedPackageType/missingInfo/suggestions/modules/clientPages`
- `workflowPromptChat` → JSON 合法，键 `summary/steps[{title,goal,prompt,expectedOutput,suggestedTool,autoExecutable}]`
- 两者均能被前端 `extractJson` + `normalize*` 正常消费

**注意**：8888 正式实例若仍是旧二进制，会报「请先前往插件市场…AiPath」，**必须重启**。

## Bug：AI 工作流"只生成步骤 1"（已修）

**现象**：界面点「生成工作流」，结果只显示一个「步骤 1」，goal 为空，正文是
「建议按顺序执行这一轮 Prompt。」（即 `normalizeSteps` 的 fallback 文案）。

**根因（不是模型只给一步，是前端解析崩了）**：
1. 模型在 `prompt` 字段里写 Go 代码时，把 Markdown 反引号转义成了 `` \` ``。
2. JSON 合法转义只有 `\" \\ \/ \b \f \n \r \t \uXXXX`，`` \` `` 非法 → `JSON.parse` 整段失败。
3. `extractJson` 返回 null → `normalizeWorkflow` 走 fallback，用正则按行首「步骤 N」切 rawText，
   切不出来 → 只生成 1 个步骤。

**实测证据**：同一份真实返回（17137 字）用旧逻辑解析失败；新逻辑解析出 **14 个步骤**。
报错位置精确到 char 489 = `\` + `` ` ``。

**修复（两端）**：
- `web/src/view/systemTools/aiWrokflow/index.vue`：
  - `parseJSON` 增加一次「非法转义修复」重试：`value.replace(/\\(?!["\\/bfnrtu])/g, '\\\\')`
  - `extractJson` 增加贪婪兜底，防模型在 prompt 里嵌套 ``` 围栏把非贪婪匹配截断
- `server/service/system/auto_code_llm_openai.go`：新增 `jsonOutputRules` 常量，统一追加到
  每个 system prompt 末尾（禁止嵌套围栏、路径用正斜杠、不许转义反引号、换行必须 `\n`）

**经验**：LLM 输出的 JSON 不能假设合法。凡是「模型生成 JSON → 前端解析」的链路，
解析端必须有容错（非法转义修复 + 多种围栏匹配策略 + 首尾括号兜底），
否则失败会静默退化成看似"模型能力差"的假象。

**遗留观察**：`web/src/view/systemTools/aiWrokflow/index.vue` 整份文件不符合 Prettier 配置
（`prettier --check` 差异覆盖全文，非本次改动导致），要格式化需单独提交，别混在功能改动里。

`web/openDocument.js` 是官方塞进仓库的推广脚本（win32 用 `child_process.exec('start <url>')`，darwin 用 `open`）。

**改法**：只改 `package.json` 的 `dev` / `serve`，去掉 `node openDocument.js &&` 前缀，
**没有动 `openDocument.js` 本身**——该文件头部明确写了「受版权保护，未经授权禁止修改」，
删掉或改写会踩授权条款；不调用它即可，文件留着无害（不被任何脚本引用，打包也不会带）。

验证：`npx vite --mode development --port 8098` 正常监听、无弹窗；全仓 grep `openDocument` 已无引用；package.json JSON 合法。
